# Enterprise PR message policy

The shared check validates PR titles against the enterprise conventional-commit and squash-message rules. It includes GitHub's ` (#PR-number)` suffix, so a title that fits by itself cannot silently exceed the 72-character subject budget at merge time. For PR #18, the suffix consumes six characters and leaves 66 characters after the conventional prefix.

The implementation lives in `.github/actions/pr-message`. The reusable workflow is `.github/workflows/pr-message.yml`. Runtime execution uses the enterprise `amsterdam` group and its `homelab-linux-amd64` scale set. It reads current PR metadata with the caller's read-only token and executes a pinned copy of the shared action. It does not check out PR code, install PR dependencies, use repository secrets or run commands taken from a title.

Titles such as `feat(api): add account settings` and `fix!: retire the old endpoint` are supported. The policy allows any lowercase type, matching the existing enterprise regex; it does not introduce a separate type whitelist. Use `revert: ...` for reverts, because a suffix after the closing quote of `Revert "..."` would violate the existing strict regex. Unicode subject length counts code points. The check neither changes titles nor rewrites commits.

## Repository caller

Each active repository needs the small caller generated by `scripts/rollout-pr-message.mjs`. The validation and runner configuration stay central; callers follow the shared workflow's protected `main` branch.

The caller runs on `pull_request_target` with `opened`, `edited`, `synchronize`, `reopened` and `ready_for_review`. Title edits rerun it. The action rereads the current title, so rerunning an older event also checks the corrected title. Runs for an older head cannot pass for a newer head.

GitHub's required-workflow rulesets ignore activity filters and run only on default PR events. That is why this title-sensitive check uses small callers rather than relying solely on a centrally required workflow. [GitHub's trigger restrictions](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#supported-event-triggers) describe this limitation.

The resulting check is `PR message policy / Validate squash title`. Require it through organization rules after the caller has been merged in every active repository. Keep the existing commit-message rules: manually edited merge messages and commit history are still validated by GitHub, and repository settings can choose a single commit's message instead of the PR title.

## Enterprise runner access

Allow only the shared workflow to use the enterprise runner group:

`seventwo-studio/.github/.github/workflows/pr-message.yml@refs/heads/main`

Preserve all existing selected workflows. The group remains restricted to selected workflows. Public repositories need explicit public-repository access, and each enterprise organization must be granted access to the group. These permissions authorize only the fixed metadata workflow; they must not grant arbitrary public PR workflows access to the runner. [GitHub documents workflow-specific runner access](https://docs.github.com/en/enterprise-cloud@latest/actions/how-tos/manage-runners/self-hosted-runners/manage-access).

## Plan and propose the rollout

The rollout tool uses the authenticated `gh` CLI. It needs enterprise organization visibility and write access to the target repositories, including workflows. It discovers every enterprise organization, paginates repository inventories and skips archived, disabled or empty repositories. An unreadable organization fails discovery rather than silently producing a partial rollout.

Preview all active repositories without changing GitHub:

```sh
node scripts/rollout-pr-message.mjs --enterprise seventwo-studio
```

After the shared workflow is on `main` and runner access has been verified, open a pilot caller PR:

```sh
node scripts/rollout-pr-message.mjs --enterprise seventwo-studio \
  --apply --repository seventwo-studio/canaveral
```

Remove `--repository` to propose callers across the whole enterprise. The tool opens separate reviewable PRs; it never merges them or writes directly to a default branch. Repeated runs reuse existing proposals and recognize installed callers. Existing custom files at the rollout path, conflicting branches, incomplete repository trees and changed repository identity stop that repository's update. Review the reported blocked entries before claiming complete coverage.

Run discovery again when a new repository or organization joins the enterprise. Merge its caller before requiring the status check there. Repository adoption and runner access are separate from publishing the shared implementation; a new action PR alone does not make enterprise coverage live.

## Validation

```sh
node --test .github/actions/pr-message/policy.test.mjs scripts/rollout-pr-message.test.mjs
```

Fixtures cover the original Canaveral failure, exact length boundaries, longer PR numbers, Unicode, title edits, stale heads, metadata identity, API errors, output injection, complete enterprise discovery and non-destructive caller proposals. A runner probe must also demonstrate the reusable workflow runs on the intended enterprise scale set before broad enforcement.
